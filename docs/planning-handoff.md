# 기획 세션 인수인계 (기획 세션 → 다음 기획 세션)

이 문서는 기획 세션을 새로 열 때 읽는 안내서다. 기획 내용 자체는 `docs/game-design.md`가 전부이고, 여기에는 작업 방식과 현재 상태만 적는다.

## 1. 역할과 규칙
- 이 세션은 **기획 전용**이다. 코드는 건드리지 않고 `docs/` 문서만 수정한다. 모든 답변은 **한국어**로 한다.
- 사용자와 진행하는 방식: **질문을 3~4개씩 묶어서** 하고, 각 질문마다 **추천안 1개와 이유 한두 줄**만 말한다. 사용자가 "추천대로"라고 하면 그대로 확정한다. 확정되면 `docs/game-design.md`에 반영한다.
- **사용자의 요구는 요약해서 되돌려 확인한다.** 예전에 사용자가 "22명이 전부 본인 스탯에 맞춰 엔진으로 움직여야 한다"고 말했는데 이를 "팀별 사이클 추상화"로 잘못 설계했다가 되돌린 일이 있다. 구현 비용이 큰 결정은 원문 그대로 인용해서 확인한다.
- **코드 세션이 돌고 있을 때는 기획서를 수정하지 않고 보고만 한다.** 확인 방법: `list_sessions`(mine: true)로 상태가 RUNNING인지 보고, `git fetch` 후 `origin/main` 로그를 본다. 쉬고 있으면(IDLE/COMPLETED) 수정해도 된다.
- 문서만 바뀌는 푸시는 `main`에도 올려도 된다(사용자 허가). **코드가 바뀌는 푸시는 사용자에게 먼저 묻는다.** 기획 세션은 자기 작업 브랜치(세션마다 다름, 직전 기획 세션은 `claude/soccer-career-planning-3wc4v9`)와 `main`을 같은 커밋으로 맞춘다. PR은 사용자가 요청할 때만 만든다.
- 커밋 메시지 끝에 `Co-Authored-By`와 `Claude-Session` 줄을 붙인다(시스템 안내를 따른다).
- **세션 이름 규칙(사용자 지시, 2026-10-15)**: 새 코드 세션 이름은 "N단계_작업 이름". **새 세션을 열 때 바로 앞 단계 세션의 제목 앞에 `draft_`를 붙인다**(`set_session_title`, 예: `draft_9단계_E3.5 5차 능력치 곡선 평탄화 (E.24)`). 새 기획 세션을 열 때도 이전 기획 세션 제목 앞에 `draft_`를 붙인다.

## 2. 사용자 선호
- 현실감을 중시한다(2018년 기준 실제 데이터, 금액도 실제와 비슷한 규모, 단 천문학적 금액은 제외).
- 캐주얼한 성장(훈련 선택이 아니라 경기 활약으로 XP를 얻고 포인트를 찍는 방식), 목표 깊이는 FM의 60~70%.
- **게임 실행 중 AI API 호출은 없다.** 전부 순수 코드(오프라인, 서버 없음).
- 비용과 세션 횟수에 상한은 없다. 다만 효율을 우선한다(세션당 한 덩어리, 필요한 섹션만 읽기).
- 코드를 직접 보지 않는다. 결과는 부록 C 소절과 `main` 로그로 확인하고, 이해하기 쉽게 설명해야 한다.

## 3. 현재 상태 (최종 갱신: 기획 세션 종료 시점)
- **완료(코드, `main`에 배포)**: 1단계, 1.5, 1.6, 1.7단계. 폼(D.1)과 부상(D.2)도 구현됨.
- **엔진 방향 확정(중요)**: 경기 엔진은 **22명이 각자의 능력치로 실시간 움직이는 에이전트 기반 시뮬레이션**이다(부록 E). 처음에 "팀별 공격 사이클 추상화"로 잘못 설계했다가 사용자 요구("22명이 전부 본인 스탯에 맞춰 엔진으로 움직여야 한다")에 맞게 전면 재작성했다. 게임 실행 중 AI API는 쓰지 않는다(순수 코드).
- **엔진 규칙 확정**: 오프사이드, 어드밴티지 룰, 퇴장 시 수적 열세 전술 변화 **포함**. VAR와 부상 시간 소모 추가시간은 **제외**. 파울과 카드 포함. 레드카드 1경기 출장정지와 옐로 5장 누적 정지는 유지로 확정(D.9).
- **개발 순서(17번)**: R단계(팀 로스터 생성기, 23번) → 2단계 경기 엔진 E1~E5(부록 E) → 3단계 카드(부록 F) → 4단계 잔여(포지션 전환/배지) → P단계(피치 고도화) → U단계(디자인 적용) → 5단계(커리어 확장, 18~22번).
- **코드 진행(2026-10-14 야간 무인 구현 결과, `main`에 반영됨)**: **R단계(팀 로스터 생성기, C.8), 2단계 E1(엔진 코어, C.9), E2(결정과 듀얼, C.10), E3(규칙과 통합, C.11) 완료**. 오프사이드, 어드밴티지, 파울/카드/퇴장, 교체, 부상, 평점, `playRound` 연결, 시즌 38경기 자동 진행(엔진 + 빠른 경기 혼합)까지 구현됐고 경기 계산은 약 0.7초다. **E4(내 선수 개입), E5(경기 화면), 3단계 이후는 아직 시작하지 않았다**(부록 H.1: 사람이 확인한 뒤에 시작).
- **엔진 통계 목표 미달 처리 결정(2026-10-14, 부록 D.9)**: 사용자가 추천안대로 확정. E3과 E4 사이에 **E3.5 현실감 보정**(부록 E.18)을 넣었다. 핵심은 ① 공이 죽어 있는 시간(재개 대기)과 스로인 빈도 ② 포지션별 득점·패스 수신 분포 ③ 팀 전술 성향 `style` ④ 판단 무작위 스케일 완화 ⑤ 표본 확대와 경량 회귀 가드 `balance:engine:check`. **사용자 원칙(중요)**: "선수들이 목표를 따라 움직이면 안 되고 스탯이 작동해야 한다. 스탯과 분포 목표의 밸런스가 관건" → E.15.1 캘리브레이션 원칙(목표는 측정, 결과 할당·고무줄 보정 금지)과 **스탯 반응 목표**(능력치 +10 짝지은 비교)를 만들었고, 충돌하면 스탯 반응이 우선한다. 이후 코드 세션이 보낸 수정 계획(컷백·포스트플레이, 역압박, 판단 단위 "골 = 1" 통일, 홈 이점 분해, CI 점검)을 받아 **E.18을 "구조 먼저(A) → 튜닝 한 번(B)"으로 개정**했다(부록 D.10). 그 뒤 **사용자가 "전술은 내가 정한다(이때만큼은 감독)"고 결정**해서 전술 시스템(성향 6종, 포메이션 + 내 위치 + 슬롯 역할, 세부 전술 4개, 부록 E.19, D.11)을 넣었다. 엔진 층은 E3.5 A8, 설정 화면은 E3.6. 디자인 요청서(`docs/ui-spec-for-design.md`)에도 전술 화면 I.16을 추가했다. 감독 신뢰도와의 관계는 D.11 6번으로 정했다(감독 = 기용 담당, 전술 = 사용자, 지시 카드 = 내 슬롯 역할을 따를지).
- **UI/디자인**: 사용자가 Claude Design으로 디자인 중이다. 요청서는 `docs/ui-spec-for-design.md`(최신, 엔진 규칙 반영), 화면 명세는 부록 I. 디자인은 "토큰/컴포넌트 시트 → 경기 화면 등 최우선 3화면(I.4, I.5, I.9) → 나머지" 순서로 진행 중이다. 산출물은 `docs/design/`에 보관 예정이고, 디자인이 도착하면 기획 세션이 화면 관련 섹션을 개정하고 U단계 적용 명세를 쓴다.
- 코드 세션은 `main`으로 푸시한다. 기획 세션은 자기 작업 브랜치와 `main`을 같은 커밋으로 맞춘다(문서만 바뀔 때).

## 6. 작업 요령 메모
- 기획서 수정은 스크립트(Python)로 문자열 교체 후 `git add/commit/push`(기획 브랜치) → `git push origin HEAD:main`(문서만 바뀔 때). 수정 전에 `git fetch`로 `origin/main`이 앞서 있는지 확인하고 있으면 먼저 병합한다.
- 수치를 정할 때는 간단한 계산(Python)으로 확인해서 근거를 보여 준다(주급 곡선, 득점 곡선 등).
- 사용자가 "ㅅㅂ" 같은 표현을 쓸 때는 대개 내가 요구를 잘못 이해했다는 신호다. 변명하지 말고 원문을 다시 확인하고 바로 고친다.
