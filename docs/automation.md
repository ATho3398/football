## 1. 단계 흐름
1. **단계 시작(기획 세션)**: 지시를 쓰고 코드 세션 "N단계_작업명"을 연다. 직전 단계 코드 세션(그리고 그 fix 세션) 제목 앞에 `draft_`.
2. **코딩(코드 세션)**: 구현 → 검증 → 배포 → 부록 C. **배포 규칙(사용자 확정 2026-10-17 22:47·22:51 KST, 시간은 아끼고 오류 추적은 쉽게)** — 바로 아래 "배포 규칙"을 따른다. 엔진을 만지다 "해결 어려움"(2번)이면 더 고치지 않고 `docs/engine-issues.md`에 기록한다.
   - **배포 규칙**:
     ① **로컬 검증이 기본 관문**: main 푸시 전에 CI와 같은 순서(`npm ci` 상태에서 typecheck → test → balance:check → balance:engine:check → build)를 자기 세션에서 모두 통과시킨다. 통과 못 하면 푸시하지 않는다. **중복 실행 금지(시간 절약)**: `balance:check`는 `balance`와 같은 스크립트(판정만 추가)라, 마지막 코드 커밋에서 `npm run balance`를 이미 돌려 회귀 가드 통과를 확인했으면 다시 돌리지 않는다. 문서·캡처만 바뀐 커밋은 재검증하지 않는다. 오래 걸리는 점검(test·balance·engine:check)은 백그라운드로 동시에 돌린다.
     ② **푸시 전 main 확인**: 푸시 직전 main 최신 CI(`actions_list`)를 본다. **빨간불이면 그 위에 올리지 않는다** — 그 실패가 이전 패치 것이면 그 세션(또는 기획 세션)에 알리고, 그 수정이 main에 들어온 뒤 병합해서 푸시. 그래서 main에는 늘 실패가 하나 이하(어느 패치 탓인지 바로 안다).
     ③ **푸시 즉시 보고, 기다리지 않음**: 푸시하면 CI를 기다리지 않고 기획 세션에 완료 보고, 기획 세션은 바로 다음 단계를 연다. 배포 시간은 패치 수와 무관(약 20분, 매번 전체 점검)이고, 연달아 오면 `cancel-in-progress`로 마지막 배포에 앞 내용이 같이 들어간다.
     ④ **CI 확인은 푸시한 세션이**: send_later 약 25분 뒤 자기 커밋이 포함된 실행을 확인한다(자기 실행이 다음 푸시로 취소됐으면 그다음 실행). 성공이면 끝(기획 세션에 한 줄). 실패하면 실패 단계·테스트를 보고 **자기 커밋에서 그 단계만 로컬 재실행** → 재현되면 자기 패치 탓 → 고쳐서 푸시·알림. 재현 안 되면 다음 패치 탓 → 그 세션·기획 세션에 알림. 러너 시간 초과류(예: 경기 계산 2초 테스트 2,068 ms)는 1회 재실행(`actions_run_trigger`)으로 확인하고, 반복되면 테스트 여유값을 고친다.
     ⑤ **기획 세션**: 사용자가 "배포해 줘/배포 상태"라고 하면 `actions_list`로 마지막 실행과 그 커밋의 부록 C 소절을 알려 주고, 필요하면 `workflow_dispatch`로 다시 돌린다. 배포 전용 세션은 두지 않는다(코드 세션이 동시에 2개 이상 돌 때 다시 검토).
3. **문제 없음**: 기획 세션에 완료 보고 → 기획 세션이 결과를 사용자에게 보고하고 다음 단계를 연다.
4. **엔진 문제 있음**:
   - 가드를 통과한 부분까지만 main 배포, 가드가 깨지면 배포하지 않고 작업 브랜치에 둔다.
   - 코드 세션 → **엔진 관리자**(`session_01ULNad1tAcSQzVKsFKN355d`, Fable, 코드 수정 금지, 2026-10-16 교체 — 인수인계 `docs/engine-manager-handoff.md`)에 send_message(기록 경로, 브랜치, 재현 명령). 기획 세션에는 짧게 알림만. send_message가 없으면 기획 세션이 대신 넘긴다.
   - 엔진 관리자: 원인 분석 → `docs/engine-diagnosis-<패치>.md`(3번의 처방 양식) → 기획 세션에 send_message.
   - 기획 세션: 모델 선택 후 **"N단계_fix_이름"** 세션을 연다. Opus 고속 = 처방이 파일·함수·상수 단위로 좁고 명확할 때. Fable = 여러 모듈이 얽힌 구조 문제이거나 같은 문제로 Opus가 이미 2번 이상 실패했을 때.

## 3. fix 세션 규칙
- **처방 양식(엔진 관리자가 반드시 적는다)**: 통과 기준(목표 지표·범위, 지킬 가드), 우선순위 가설 최대 3개(가설마다 손댈 파일·함수·상수), 재현 명령과 현재 측정값.
- **예산**: 2시간(CI 대기 제외, 1시간에 중간 점검), 측정 최대 6회(가설 3 × 조정 2), 빠른 표본으로 판단하고 전체 시즌 점검은 마지막 1회. 비용 상한 Opus 10달러 / Fable 20달러(자기 `get_session`의 비용).
- **실패 판정(하나라도 해당하면 즉시 중단)**: ① 2시간 초과 또는 비용 상한 초과 ② 가설 3개 소진 ③ 연속 2회 시도에서 남은 차이가 25% 이상 줄지 않거나 나빠짐 ④ 목표를 맞추면 다른 가드가 깨지고 1회 더 고쳐도 둘 다 통과 못 함 ⑤ 진단 불일치: 시작 20분 안 측정에서 처방이 가정한 원인이 재현되지 않음 ⑥ 범위 밖(세이브 구조·화면·다른 시스템 수정 필요, E.15.1 위반).
- **결과 처리**: 성공(기준·가드 통과) → 배포, 보고, 다음 단계. 부분 해결(남은 차이 50% 이상 감소 + 가드 통과) → 배포, 나머지는 미해결 목록. 실패 → 배포하지 않고 브랜치에 기록(시도와 측정값) → 기획 세션 보고 → 다음 단계.
- **진단 불일치(⑤)**: 그 문제에 한해 엔진 관리자에게 1회 되돌려 재진단 → 재진단 뒤 fix도 실패하면 미해결로 넘긴다.

2. **보고 후 0**: 마지막 보고 이후 디자인 없는 새 화면·큰 패널 **6개 이상**, 또는 그런 화면이 있는 단계 **3개 이상**, 또는 사용자 화면 불만 → UI 세션이 **사용자에게 바로 보고**(`docs/ui-requests/<N>.md`, 캡처 `docs/ui-requests/<N>/`, 폰 390×844·PC 1280×800 Playwright): ① 왜 필요한지 ② 필요한 업데이트 내용(화면별 목적·데이터·상태) ③ Claude Design에 붙여 넣을 프롬프트. **프롬프트 전달(사용자 지적 2026-10-17 21:01 KST)**: 사용자는 브랜치 파일을 열어 복사하기 어렵다. 그래서 보고 답변 **본문에 프롬프트 전문을 코드 블록 하나로 그대로 붙인다**("`<N>.md` 맨 아래 참고"처럼 경로만 주는 것 금지). 같은 내용을 `SendUserFile`로 `<N>_ClaudeDesign_프롬프트.txt`(스크래치패드)와 첨부할 캡처 묶음 `<N>_캡처.zip`(폰·PC)으로도 보낸다. 디자인 묶음 `player-one-design/`도 첨부가 필요하면 zip으로 같이 보낸다. 기획 세션에는 한 줄 알림. 보고 뒤 개수는 0. 다시 조건만큼 쌓이면 **새로 쌓인 것만** 다시 보고(차례 N+1).

## 7. 비용·용량 (사용자 확정 2026-10-19 20:52 KST, 마스터 R 누수 점검)
- **응답당 비용 = 대화 크기**: 기존 대화를 다시 읽는 값이 약 0.2달러/100만 토큰이라 도구 한 번 = 대화 40만이면 약 0.08달러. 누적 금액이 아니라 **지금 대화 크기**로 판단한다.
- **코드 세션 나누기**: "10달러"는 참고선이다. 나누는 기준은 남은 일의 양 — 하위 단계 하나 이상 남았고 대화가 40만 토큰을 넘으면 새 세션, 마무리(검증·배포·CI·보고)만 남았으면 이어간다. 단계는 처음부터 a/b로 작게 연다.
- **오래 사는 세션**(마스터 50만, UI·엔진관리자 40만 토큰)은 대화 크기로 교체한다. 대기 중인 큰 세션(특히 Fable 엔진관리자)은 깨우지 않는다 — 마스터 교체 알림 보내지 않음, 엔진 블록 시작 때 새 엔진 관리자로 교체(인수인계 `docs/engine-manager-handoff.md`).
- **큰 출력 받지 않기**: 테스트·balance 로그, 세션 목록, 긴 파일은 통째로 받지 말고 `tail`·`grep`·필요한 소절만. 로그는 파일로 남기고 요약만 본다.
- **확인 캡처**: 레포에는 패치당 5~10장(핵심 화면, 폰·PC)만 커밋하고 나머지는 세션 작업 폴더에만 둔다(레포가 커지면 세션 시작·배포 때마다 내려받는 양이 늘어남).
- **세션 보관(archive) 안 함**: 0번 참고.
- **docs 병합은 `git merge`로만**(2026-10-19 C.74a 사고): 마스터·UI·엔진 브랜치 docs를 `git checkout <브랜치> -- docs/`로 가져오면 main 부록 C 등 다른 세션의 내용이 덮어써져 사라진다. 반드시 `git merge origin/<브랜치>`로 합치고 충돌만 손으로 푼다.
